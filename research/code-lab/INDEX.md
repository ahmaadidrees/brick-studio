## Evidence notation and scope

| Label | Meaning |
| --- | --- |
| Source / date / confidence in a table row | Applies to that row’s factual claims. Source links identify official documentation, pinned code, original research, community reverse engineering, or another stated type. Dates distinguish publication/version from the date inspected. |
| High | Directly specified by inspected primary material; not a claim that the proposed fixture was executed. |
| Medium | Source supports the description, but integration, host behavior, limited study design, or secondary evidence constrains the conclusion. |
| Low / unverified | Incomplete access, conflicting values, unpinned implementation, or a lead not sufficiently verified. Never use as a conformance requirement without further work. |
| Proposed / inference / derived | Original Brickgineers design advice, test design or transparent arithmetic—not a product feature, measured benchmark or educational finding. |
| Evidence priority | For runtime behavior, pinned implementation outranks informal descriptions of the same version. Official manuals establish supported authoring workflows; community reverse engineering remains useful but does not become Nintendo source code. |
| Existing product decisions | The user’s brief is authoritative for Code Lab’s intended design, not evidence that another product already implements it. The library does not substitute scratch-vm for your own runtime. |

## Architectural tensions to preserve in the backlog

These are implications of the sourced facts above, not a recommendation to discard the existing design.

| Tension | Explicit decision/test needed |
| --- | --- |
| Scrolling world vs stage-fenced motion | Define the stage/world boundary and separate extension motion names where semantics differ. See §1. |
| Wall-clock Scratch scheduling vs deterministic replay | Define a versioned scheduling contract and test intentional profile differences. Replacing the RNG alone is insufficient. See §§1, 5. |
| Shared brick definition vs one copy’s code | Make template editing, per-copy properties and independent/forked code distinguishable; specify propagation and undo. See §2. |
| Pixel-based Scratch sensing vs platformer body collision | Maintain separate contracts; benchmark pixel sensing without substituting bounding boxes under the same block name. See §§1, 4, 10. |
| Editable text vs faithful block reconstruction | Use a constrained intermediate representation and explicit unsupported-code behavior. See §6. |
| Student creativity vs publication safety | Preserve private authoring while adding clear classroom/public publication permissions and review. See §9. |

## Updating this library — proposed maintenance procedure

| When | What to update |
| --- | --- |
| Changing runtime or Scratch oracle | Record the new full commit and configuration; rerun behavior traces and review renderer-dependent changes before replacing expected outputs. |
| Upgrading Blockly or plugins | Check release notes and peer dependencies, then run old-project serialization, custom-procedure, undo, touch and accessibility fixtures. |
| Adding a Platformer block | Write its own visible semantics and collision/timing tests; do not inherit an undocumented native engine default. |
| Enabling multiplayer | Require canonical state-hash replay across engines and slow devices, including block scheduling, random values, assets and side-effect deduplication. |
| Changing sharing, recording, analytics or a subprocessor | Recheck legal authority, privacy notice, school agreement and retention/deletion implementation with the responsible school/privacy reviewer. |
| Expanding the device baseline | Measure the actual managed fleet. Example specs and proposed workloads in §10 are not measured capacity claims. |
