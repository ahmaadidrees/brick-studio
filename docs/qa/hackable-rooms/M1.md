# Hackable rooms M1: play together, November 3, 2026

The owner said "Yes, start M1". This is M1 from `README.md`: a Hackable project played by several people at once,
each with their own Hero (or Car). It is built on the M0 groundwork (`M0.md`).

**Branch:** `claude/hackable-rooms`, committed locally and not pushed or deployed. The Worker has a new Durable Object
class and a `v5` migration, so deploying it is a Worker deploy as well as a site deploy.

## How it works for kids

- **The owner starts a room:** in the studio, ⋯ (This project) → **Play together**.
  - A room bar under the header shows who is playing, the link to send (Copy link) and **Stop playing together**.
  - A project kept in this browser opens a room joined by link (`/2d/hackable/r/<room>`).
  - An account project opens its class room (`/2d/hackable/w/<project>`): classmates it is shared with join with
    their class sign-in.
- **Joining:**
  - The link opens a page asking for a name (link rooms) or a sign-in (class rooms).
  - Then it shows the game, full screen, with the kit's HUD and touch buttons.
  - Each player gets their own Hero, and the camera follows it.
- **While the room is open, the owner's studio plays the room's game.**
  - Play and the Code preview show the room's game, not a private copy.
  - The owner's changes go to everyone about a second after they stop: the bricks change live, and anything about
    the level (placing, painting) shows on the next Restart.
  - **Restart** starts everyone again from the project as it is now.
  - Guests have no Pause or Restart: a room's game can't be paused on one screen.
- **Someone joining a game already going:** the owner's bar says "Sam joined. Press Restart to start everyone
  together."
  - This matters for Racing: the Starter's "go" is broadcast once, so a Car that arrives afterwards waits for the next
    race.
- **Saving:** the owner's studio saves the project exactly as before. The room never saves anything to the account.

## What's built

| Piece | Where | What it does |
|---|---|---|
| **Protocol** | `src/platformer/lab/rooms/protocol.ts` | The classic room protocol without poses. **Events:** `join` and `leave` (made by the room), `key`, `project` (the host's project as `designText`, live or restarting), `restart`. Ticks are 30 a second, so `MAX_LATE` 15, `MAX_EARLY` 5, fingerprint every 60, keyframe every 600. Projects and keyframes up to 900 KB; other messages up to 16 KB. |
| **Room logic** | `rooms/roomCore.ts` | `HackableRoomCore`, the twin of the classic `RoomCore`: one clock, one order, joins and leaves a few ticks ahead, the provider's fingerprint as the reference, and a fresh copy for anyone who disagrees. **Checks:** only the host may send `project` or `restart`; a project must pass `save.parse` and keep its kit (no switching a race to a platformer); at most two project edits a second; a keyframe must sit on its tick, come after every earlier event, and carry no bricks (the room adds the project itself). Also a `sync` request for a game too far behind to catch up. |
| **The game's side** | `rooms/game.ts` | Applies each event: join (a Hero from the kit's player brick), leave, keys per player, a live edit (bricks replaced, never changed in place), and restart (a fresh game, the clock carrying on, players kept). `world.design` (new in `core/contracts.ts`) holds the project the game runs, shared between rewind copies like the bricks, so going back past an edit goes back to the old project. |
| **Session** | `rooms/session.ts`, `rooms/link.ts` | `HackableRoomLink` (connection, clock, reconnects; the classic `RoomLink` for this protocol) plus the M0 `HackableTimeline`. It plays up to the room's clock each frame, and every 100 ms while the game is off screen. It sends fingerprints for ticks nothing can change any more, and keyframes when it is the provider. Our own keys are stamped at the room's tick now, after catching up. |
| **Screen side** | `rooms/session.ts` `facade`, `studio/store.ts` `StudioRoom`, `studio/Stage.tsx` | Screens get a `Runtime` stand-in. It reads the room's game and sends our keys to the room, but does nothing for anything that would change the game on one screen only: the mouse, clicks, stop, step. The Stage's room loop plays to the room's clock and draws the real game, blending between ticks. Sliders don't touch a room's game (the edit goes out instead). Ask/answer is off in rooms. |
| **Studio** | `studio/StudioApp.tsx`, `rooms/studioRoom.ts`, `rooms/RoomBar.tsx` | Play together, the room bar, live edits after 800 ms, and Restart for everyone. |
| **Join page** | `rooms/RoomPage.tsx`, `routes2d.ts`, `PlatformerApp.tsx` | `/2d/hackable/r/<room>` and `/2d/hackable/w/<project>`. |
| **Worker** | `multiplayer/worker/src/hackableRoom.ts`, `classroomRoutes.ts`, `classroom/index.ts` | **The Durable Object** `HackableRoom`: sockets that hibernate, rate limits, classroom re-checks (host actions need a check under 15 s old), and the project kept in storage while the room lives. **Routes:** `POST /hackable/rooms`; `GET /hackable/rooms/<id>(/connect)`; `POST /classroom/worlds/<id>/hackable-ticket` (audience `brick-hackable-v1`); `GET /hackable/worlds/<id>/connect`. `loadClassroomHackable` reads an account project without its workspaces. Access changes reach Hackable rooms too. **Config:** `wrangler.jsonc` adds the `HACKABLE_ROOMS` binding (prod and staging) and migration `v5`. |

Small supporting changes:

## Decisions taken in M1 (worth a look)

- **Only the host changes the project.** The owner (link rooms), or the owner and the teacher (class rooms).
  Classmates play. Roles are M2 and owner decision 3.
- **Play doesn't restart everyone unless the project changed;** Restart always does. Otherwise an owner glancing at
  Build and back would restart the whole room.
- **Level edits (placing, painting, knobs) show on the next Restart;** code and costume edits are live. Live level
  edits are M2's Builder role.
- **No account saving from the room in M1.** The owner's studio saves as always. A class room starts from the
  account's copy whenever nobody is in it.
- **Not shared in rooms yet:** ask/answer, the mouse and clicks. Each screen's mouse is its own. They need the M2
  per-player blocks.

  sheet).
- **New blocks:** "when a player joins", player names, per-player variables. The HUD (coins, laps) shows the first

- **Not tried yet:**
  - real devices and real network lag (the in-process test used 30–60 ms each way; the browser test was local);
  - Firefox;
  - a deployed Worker;
  - kids' bigger projects (painted costumes push a project toward the 900 KB limit).
- **Racing's keyframe** includes every track cell: about 600 KB raw every 20 seconds from the provider, and a copy every
  4 ticks costs about 3 ms (M0). Leaving the unchanged cells out is the next thing to do for Racing rooms.
- **Reconnects:** done in `SHIP.md` (a dropped player keeps their Hero for 30 s). The dev hook `window.__hackableRoom`
  is dev only.
