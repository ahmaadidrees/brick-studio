## Part 1: each player is on their own

**The bug on production:** in a room, a Walker touching one Hero hurt every Hero, and one player reaching the Goal
stopped the game for everyone. The Walker, Spikes, Lava and the Goal are ordinary bricks: they broadcast "hero hurt" or
"course clear", and the Goal says "stop all". Broadcasts reach every Hero, and "stop all" stops everything.

**The fix is in the language, not in the bricks,** so kids' own bricks get it too:

- **A script knows which players it is about** (`ThreadHandle.about`, `core/runtime.ts`). It is set when the script
  touches a player's Hero ("touching Hero?", `core/sensing.ts`), when a player's Hero bumps the brick (`core/platformer.ts`
  bump hats: Spikes), and it is passed on by the broadcast that started a script. A script on a player's own Hero is about
  that player.
- **A broadcast about some players reaches only their Heroes.** Bricks that are no one's (the Stage, a Coin, the Starter)
  hear everything, as before. So a Walker's "hero hurt" hurts only the Hero it touched, a Spring launches only the Hero on
  it, a stomp bounces only the stomper, and "coin collected" still counts for everyone.
- **"y position of Hero" reads that player's Hero** in a script about a player (before, it always read player 1's: a
  Walker judged every stomp by player 1's height).
- **"stop all" in a script about players finishes only them** (`PlayerSlot.finished`, the tick). Their Hero and its clones
  stop and sit out the round: no scripts start on them, and nothing touches them (so the Goal does not finish them twice).
  The game goes on for everyone else. **The round ends** (a real stop all) when every player has finished, or when the
  last player still going leaves. The host's Play again starts a new round.
- **Solo play is unchanged:** with no players nothing is "about" anyone and "stop all" stops all.
- **Determinism:** `about` is kept with each thread in snapshots, keyframes and the fingerprint (`core/snapshot.ts`), and
  `finished` lives in `world.players`, so every game and every late joiner agrees.

**The screens** (`studio/builder/PlayFeedback.tsx`, `rooms/FinishNotices.tsx`, `studio/race/screens/RaceHud.tsx`):

- your own "You made it!" comes from the game itself (your slot finished), and "Try again" only for your own Hero;
- everyone else sees a short notice, **"Sam finished, 0:42.3"**, or in Racing **"Sam finished, 41.3s"**;
- in a room only the host starts the next round: a classmate's card says "Others are still playing. The host starts the
  next round." with **Watch the others**, then "Everyone has finished." The host's card keeps Play again (Race again);
- names are the room's current names (someone who renamed themselves after joining shows the new name), and a late joiner
  counts from the game's own green flag, so every screen shows the same times.

**Racing** already finished per car (each Car stops itself and writes its own result), and does not stop the race. What
it lacked was the notice for the others and a host-only Race again; both are added. A race is over for each player when
their Car crosses the line; the results card lists who is still racing.

## Part 2: building together

### How it works for kids

- **In a room, classmates can build at once:** place and move copies, paint cells, turn sliders. Everyone sees it live in
  the game they are playing (no Restart needed: M1 showed level edits only on the next Restart).
- **Code starts off.** The host turns it on in the **Room** menu, for everyone ("Turn code on for everyone") or one player
  at a time ("Let Sam change code"); "Stop everyone building" locks building. A classmate with code gets the studio's
  Code screen with the room's real blocks; without it, Code is greyed out with "The host hasn't turned on code for you
  yet. You can build and play."
- **A live code edit restarts only that brick's scripts** (its clones go, its copies start again from the green flag);
  every other brick keeps running. Everyone sees "Sam changed Walker's code. Its scripts started again."
- **Who is editing what:** each name in the room bar shows "· Building" or "· Walker's code", and a code badge for
  classmates who may change code.
- **Changes:** a menu in the room bar lists the last 20 changes ("Sam placed Coin", "Ben painted 7 cells", "Sam changed
  Walker's code"). You can put back your own; the host can put back anyone's, and the Room menu has **Undo last change**.
- **The join page is the studio** (Build · Code · Play) for anyone who may build; a player who may only play gets the game
  alone, as in M1. The save chip says "Shared world".
- **Saving:** a class room saves the shared project to the class project itself (below). While the owner's studio is in
  its class room it does not save on its own ("The room saves this project for everyone while you play together"), and
  it carries on from the account's newest version afterwards. A link room keeps the project in the room; the host's
  studio follows every edit, so the host's own copy has everyone's work.

### Decisions taken here (worth a look)

1. **A script on a player's own Hero is about that player** (Part 1). So a Hero's broadcasts reach only that Hero among
   the Heroes (bricks that are no one's still hear them). Tag-style games work through touching: "touching Hero?" on one
   Hero makes its script about the Hero it touched. A Hero's own "stop all" finishes its player.
2. **A finished Hero sits out** until the round ends: it stands where it finished, untouchable, its keys ignored.
3. **Adding a new brick is building**, so a classmate can place any brick from the drawer. Changing an existing brick's
   costume, sound or name is code (the "Open" layer).
4. **Undo puts back what the change replaced,** even if someone changed the same thing again since. The history is short
   (20) and shared; anyone sees it, only the author or the host can use it.
5. **On a save conflict the room's version wins** and the other one is kept as a recovery copy. Rebasing the room's edits
   onto the other version (as classic 2D rooms do) is possible with the operations but not built.
6. **Two coders on the same brick:** the presence line says who is editing what; if both change it, the last change wins.
7. **Restarting a brick restarts its green-flag scripts.** For Racing's Starter that means the countdown runs again;
   for a Car mid-race it waits for the next "go".

## What is not verified

- **Class rooms in a browser** with real class sign-ins: the roles, write-behind saving and the recovery copy are covered
  by the Worker tests (the real Durable Object with the classroom fixture), not by a browser against a real database.
- **The owner's studio pausing its own saves in a class room** and resuming from the account's newest version: not run
  in a browser (needs a signed-in account project).
- In round 1 the host's local copy of the project did not have the room's edits after Vite hot-reloaded the page; in
  round 2 (no hot reload) it did. Not reproduced without a hot reload, but worth a look in the class test.
- Two coders editing the same brick at once; a project whose blocks are near the 900 KB limit; real devices, real network
  lag, Firefox, a deployed Worker.
- The recovery copies have a route but no screen yet.
- The Changes history lives in the running room only: if the Durable Object restarts or hibernates and wakes, the
  project, blocks and who may code are kept, but the list of changes starts empty.
- `rewinds` stayed 0 in the browser runs (the tabs share one machine, so other players' keys arrive before their tick);
  rewinds with edits are covered by the in-process tests with 45 ms lag each way, and by lockstep.

## Deploy order

1. **Worker first:** `multiplayer/worker`, `wrangler deploy` (staging, then production). No new Durable Object class and
   no migration: `HackableRoom` keeps one more storage key (`workspaces`) and recovery copies (`recovery:<id>`). It is
   backward compatible with the site in production: that site never sends `edit`, and ignores the new fields.
2. **Then the site** (Vercel). The new site needs the new Worker: an old Worker refuses `edit` events (the studio would
   just go back to the room's project) and has no blocks to hand out.
3. After deploying, a smoke test: open a Hackable project's room from the studio, join it in a second browser, place a
   brick from each, turn code on for the second player from the Room menu, and change a brick's code there.

No database migrations.
