## Requests for the lead

1. **`/build?world=<id>` (W6).** Open on your own world links there (`buildHref` in `worldsData.ts`). The editor
   needs to load that account world as the active world (the `onOpenWorld(document, world)` path `ClassroomPanel`
   already uses) and, when the id is unknown or no longer readable, show a plain message with a link back to
   `/worlds` instead of an empty studio. Signed-out visitors on that URL should land on
   `/join?mode=signin&next=/build?world=<id>`. Resolved as of the lead's follow-up: Join and Visit no longer use it.
2. **Owner's class on a shared personal world.** Shared personal worlds arrive with `classId: null`, so a teacher
   with more than one class cannot be shown which class a student world belongs to; the page currently lists every
   shared personal world under each class section. An `ownerClassId` (or reusing `classId` on the read model) fixes it.
3. **W2 header.** `src/shell/AppHeader.tsx` does not exist yet, so `src/pages/worlds/PageHeader.tsx` is a local
   header with the same contract (brand lockup home link, "Open the studio", account chip with the account menu).
   Delete it and swap in `AppHeader variant="page"` plus `useClassroomSession()` when W2 lands; the page passes only
   the session and a sign-out callback.
4. **W1 mock client.** `src/pages/worlds/worldsFixtures.ts` is a stand-in for `src/classroom/mockClient.ts` with the
   fixture set the contract lists. When W1 lands, the fake can be replaced by importing the mock client —
   `WorldsClient` in `worldsData.ts` is the only seam.
5. **Live-room read-only state.** Visit relies on the live HUD's existing `permission.canEdit` rendering. Worth a
   pass from W6/W7 that a viewer who cannot edit sees that state on arrival rather than failing edits.

Taken from W1 as agreed: `classCanEdit` on the world (the page reads it with a `canEdit` fallback), `teacherName`
on the class (nullable, with the "Your teacher" fallback). The visits chip is gone — no data source.
