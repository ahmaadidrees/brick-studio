## Recommendation

Build robotics as a new, bounded subsystem inside the current Brick Studio experience. Reuse the current brick authoring, validated document boundary, geometry, classroom save/recovery, and scene infrastructure. Do not revive the old Rover Island application as the foundation. Its executable behavior is a fixed-track demonstration, not a programmable robot engine. Do not estimate a percentage of reusable robotics code from the presence of Rapier, an `assembly` compiler, or a `program` object.

The first architecture decision should follow three small experiments: compile a selected, explicitly identified assembly without changing its bricks; drive that assembly in a disposable simulation scene while preserving exact authoring state; and execute both an autonomous sequence and a student-authored keyboard program through one actuator boundary. Keep cloud/live integration behind a later compatibility gate. Broad motors, sensors, and stationary machines should fit the identity and capability model from the start, while the first simulator supports one declared rover topology.

## Document boundary and compatibility are the first integration gate

Current durable schema is v2, or v3 for expanded builds; v1 is normalized on load. It contains only library version, environment, custom definitions, optional plate size, and bricks (`packages/brick-core/src/brickDocument.ts:6–35,157–171`). Validation rejects unknown schema versions (`181–183`), reconstructs every brick with known fields (`120–148`), and reconstructs the document (`241–248`). **Adding `robotics` or `program` properties to a v2/v3 object is not a compatible extension: normalization will discard them.** Local save validates then serializes the supplied object, whereas load normalizes it (`src/brick/documentPersistence.ts:54–88`), so an apparent successful local write is especially weak evidence.

Use a new explicit document version when robotics becomes persistent, provisionally v4. Keep v1/v2/v3 worlds usable without robotics and do not eagerly rewrite every world. Proposed envelope, subject to the POC results:

- `assemblies`: stable assembly ID, label, explicit member brick IDs, root/pivot and authored spawn transform, topology/compiler version, device instances and mount/port bindings.
- `programs`: stable program ID, language/format version, durable editor representation plus an executable representation with explicit provenance/compatibility. Select one source of truth; do not let two editable representations diverge.
- Bind program to assembly and devices by stable IDs, not palette position, scene object handle, or student-visible label.
- Exclude simulation position, physics handles, velocities, current keys, instruction cursor, telemetry, and completion effects from the project document.

This is a proposed contract, not a committed design. A first POC may use a separate ephemeral envelope around an immutable current document, provided its UI clearly says the prototype is not saved. Durable implementation must validate reference integrity, per-world/per-assembly device and block counts, serialized bytes, compiler versions, missing/deleted members, device compatibility, finite transforms, and program resource budgets. Retain current whole-grid/quarter-turn brick authoring; robot runtime poses need continuous transforms in a different type. Do not write simulated floats back into `BrickInstance`.

All of the following must be updated together before claiming persistence:

1. Shared validator/normalizer/factory and both document import/export paths; plate resizing currently rebuilds metadata (`brickDocument.ts:253–261`) and would drop newly omitted fields.
2. Store metadata setter, import, restore, New Build and undo/redo (`src/brick/store.ts:495–502,959–1089`). Those paths enumerate metadata fields, so extending TypeScript types alone does not preserve data. Robot membership/program changes need atomic history; delete/duplicate/paste must remap or invalidate cross-references deliberately. Current clipboard has no assembly/program data.
3. Local autosave subscriptions: brick changes trigger automatically (`documentPersistence.ts:132–134`), while metadata changes are separately scheduled from three app-owned fields (`useBrickStudioDocuments.ts:44–52,97–108`). A program-only edit must schedule a save. App metadata synchronization also enumerates fields (`BrickStudioApp.tsx:1412–1429`).
4. Cloud autosave/recovery: currently subscribes to brick or metadata identity and serializes `getDocumentSnapshot()` (`src/classroom/useClassroomWorld.ts:59–65`). Include new authoring edits without scheduling on runtime telemetry. Exercise pending recovery, conflict, account/world switching, and revision-bound save.
5. Published snapshots: `src/brick/publishedWorlds.ts:80–93` normalizes documents after decoding. Preserve programs/assemblies in publication and explicitly choose whether opening a publication permits running a program; loading should not itself imply Run authorization.
6. Live protocol/worker/classroom ingress. Client advertises literal schema `3` (`src/brick/liveRoomClient.ts:354`); classroom proxy only forwards literal `3` (`multiplayer/worker/src/classroomRoutes.ts:294`); worker replacement compatibility is explicitly `schemaVersion === 3` (`worldRoom.ts:797–799`). Generalize capability comparison; do not merely allow v4 in one validator. Reject incompatible edits safely while preserving the document.

The global custom part registry is another boundary: `packages/brick-core/src/parts.ts:112–117` deletes/replaces current runtime definitions. `brickPhysicalShapes` looks up that global map (`455`). Freeze or compile a document-scoped part map into each simulation snapshot. Otherwise opening/reloading another document could alter definitions under a supposedly frozen runtime.

## Selection, assembly, and simulation separation

For the initial topology, selection should become an explicit named assembly through a command. Validate one supported chassis/drive arrangement and explicit device mounts; report detached decorations and ambiguous components. Avoid automatically absorbing every touching brick: a parked rover touching a ramp must not absorb the ramp. Assembly membership and mechanical connectivity are separate concepts; geometric adjacency alone does not certify a joint or stud connection.

A conservative first representation leaves member bricks in the existing world authoring list and adds an assembly membership overlay. The compiler resolves their authored transforms into local coordinates around a stable pivot. This preserves current editor behavior while proving the model. During simulation, render/collide stationary world bricks separately and omit member IDs from that set; render each member under its assembly root exactly once. A later nested object representation is possible, but first demonstrate that the overlay survives moving, rotating, duplicating, deleting, resizing, and changing plate size.

Run should produce an immutable `RunSnapshot` containing document revision/content hash, resolved parts, selected assembly, compiled program, simulation configuration, and an input policy snapshot. Instantiate disposable Rapier objects and runtime state from it. Stop clears actuator outputs; Reset destroys/recreates runtime state from the same snapshot; returning to Build reveals the unchanged authored arrangement. If authoring changes, require/rebuild a new run snapshot rather than silently hot-swapping it. A moving live world needs the same explicit revision rule.

The authoring store may expose run controls, but frame-by-frame pose/telemetry must live in refs or a separate runtime store. Existing autosave and live diffing watch `bricks`; using brick transforms as animation state would create history/save traffic and live edit rejection. Existing live subscription reverts brick edits outside Build (`src/brick/liveRoomClient.ts:960–968`).

Both autonomous and student-programmed live controls should emit the same bounded actuator command. Keyboard/button state is program input; a “when Up pressed” or continuously sampled key block must actually determine motor output. A default driving assist may supply commands only under the teacher's explicit free-drive policy. Turning that assist off must not remove student-authored keyboard input. Keep the policy separate from Build/Explore room mode, edit permission, and room access lock. No current schema/protocol field implements this policy.

## Collaboration and classroom boundaries

The current live protocol has brick commands, document replacement, Build/Explore mode, lock, profile, and avatar pose messages (`packages/brick-core/src/protocol.ts:14–75`). There is no robot authority, control lease, run epoch, device command, program operation, physics snapshot, or teacher free-drive policy message.

Brick diff subscription observes only brick changes (`liveRoomClient.ts:951–970`); whole-document replacement is owner-only and revision-checked (`1008–1025`; worker `783–799`). Thus program/assembly metadata cannot transparently join existing collaborative editing. Reusing whole-document replacement for every block drag would also make ordinary student program edits owner-only and conflict-prone. Design bounded atomic authoring operations or an explicit separate editor ownership phase before enabling coediting.

Existing avatar pose is unsuitable as authoritative robot motion. The worker checks finite values/rate and rebroadcasts them (`worldRoom.ts:998–1023`); it does not simulate motion. Pose messages also follow an early path (`642–645`) distinct from mutation reauthorization. This is not proof of a current access vulnerability, but it is a reason new control messages must be intentionally placed under the appropriate policy and authority checks. Preserve current classroom read-only/edit guards (`658–667`) and owner mode controls (`936–951`) without treating those as the new teaching policy.

First prototype locally. A later shared-simulation gate must demonstrate controller exclusivity, late join, disconnect/blur stop, restart epoch, scene reset, stale messages, teacher-policy revocation, and snapshot revision agreement. A synchronized “Run” button alone does not prove synchronized simulation.

## Staged proof-of-concept experiments and worker boundaries

These are prospective implementation lanes, not work executed in this audit. Freeze interfaces first. Each lane owns its new directory; one integrator alone changes shared application/store/scene files. Do not put separate workers simultaneously in BrickStudioApp, BrickStudioScene, store, or brick-core schema.

| Stage | File-disjoint lane | Experiment and exit gate |
|---|---|---|
| 0: contract fixtures | `src/robotics/contracts/**`, fixtures only | Express one customizable rover and one stationary motor/sensor concept with the same device IDs/capabilities. Prove invalid membership, duplicate device IDs, unsupported mounts, and deleted references are diagnosable. No broad mechanical promise yet. |
| 1A: assembly compiler | `src/robotics/assembly/**` | Compile selected current bricks into a local-root immutable descriptor. Include rotated slope/arch/custom template; test 64/96/128 plates and all quarter turns. Compare rendered/collider positions and verify no duplicate static members. |
| 1B: program adapter | `src/robotics/program/**` | Blocks → bounded program representation → actuator trace, independent of React/Rapier. Autonomous drive/turn/wait/stop and student-key-controlled differential commands must use one output interface. Prove Stop, input release, step budget and missing-device behavior. |
| 1C: runtime adapter | `src/robotics/runtime/**` | Consume the fixed assembly descriptor and actuator trace in a disposable harness. Test turning, collision, ramp, stopping, sensor direction, bad spawn, and repeatable Reset. Runtime team chooses fidelity only after those observed results. |
| 2: integration shell | Integrator owns `BrickStudioApp.tsx`, `BrickStudioScene.tsx`, `store.ts`, route/feature gate | Join POCs in the existing editor. Prove select → configure → code → run → stop/reset → Build; controls do not move avatar or editor behind block workspace. Document, selection/history policy, and save count remain correct. Compare actual Chromebook frame/input behavior. |
| 3: persistence | Single schema/persistence integrator owns `packages/brick-core/**`, document hooks, recovery, app metadata | Adopt version only after contracts stabilize. Exact round-trip across local reload, export/import, undo/redo, plate resize, publication, cloud recovery; old versions remain valid, unsupported versions preserve existing data. Program-only edits persist. Runtime ticks never save. |
| 4: collaboration/policy | Worker/backend lane owns new robot protocol modules; integration of existing client/worker files serialized | Version negotiation, authoring operation validation, teacher assist policy, runtime authority, reconnect/late-join proof. Do not enable shared robots before evidence resolves authority conflicts. |

Before committing broad machine architecture, the stationary concept fixture must show that “robot” does not imply wheels, keyboard ownership, a rider, or locomotion. Before committing a drivetrain, experimentally compare sensor results and movement against the learning behavior promised by its blocks. Before committing a document model, deliberately remove a motor, duplicate a programmed rover, and shrink the plate; the intended references, diagnostics, undo behavior, and saved output should be reviewable.
